fix(opencode): deny explicitly on dialog close, audit real denial cause

Three defects made a confirmed command look like a user refusal:

- tui.ts called dialog.replace(render) without the onClose callback, so
  ESC or a backdrop click left the request unanswered. The server then
  waited out the full 60s deadline and reported "ditolak oleh user",
  blaming the user for a dialog they never dismissed on purpose.
- Both confirm and cancel called api.ui.dialog.clear(), which can itself
  fire onClose. A late close could race the allow response and flip it
  to deny. Settling is now guarded by a one-shot flag so the first
  decision wins.
- guard.ts recorded every unapproved ask as "ditolak oleh user", hiding
  timeouts and headless runs. GuardDeps.confirm now returns a
  ConfirmResult carrying an optional denialReason; adapters report
  "approval timeout" / "TUI tidak aktif" and the audit line reflects it.
  Bare booleans still work, so existing adapters and tests are unchanged.

Also verified the four false positives from commit 345fa9c still hold on
HEAD: quoted heredocs, single-quoted $, read-only sed, and git commit
messages containing $ or backticks all classify as allow, while an
unquoted heredoc carrying rm -rf / still blocks.

502 tests pass, tsc --noEmit clean.
